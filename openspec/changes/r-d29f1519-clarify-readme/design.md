# Design

## Context

動機・文案はproposal.mdを参照。実装対象を1行目の見出しではなく3行目に固定し、改行を含む非対象バイトの保持を技術的に明確にするための最小designである。機能・構造変更はなくBMAD Architectureは不要。

## Goals / Non-Goals

**Goals:** 承認後に1行だけを置換し、非対象部分のバイト同一性と範囲逸脱を直接検証できるようにする。

**Non-Goals:** README全体の再整形・全文翻訳・バージョン更新・新機能・新依存。ここでは文案を承認したり製品を編集したりしない。

## Decisions

1. バイト単位の行境界を保持して3行目のみ置換する。全文の文字列再出力や改行正規化は保持条件を壊すため採用しない。原本は `69b97f1c9dfa7211367a9bdd0af885d80d8bf380:README.md`。
2. 承認後に `.planning/argonauts/r-d29f1519/` 配下へ検証入力・検証ファイルを置く。製品テストの新規ファイルをルートのtests等へ追加しない。検証は原本と承認済み期待文字列を入力として、旧文では失敗し、置換後に成功するよう計画する。
3. 品質は一致・不変性の自動検査だけでなく、対象1行の意味と用途の言い換えを文字の証拠に残す。PMへ画像・圧縮ファイルの閲覧を要求しない。
4. 全git差分（追加・削除・rename、staged/unstaged/untracked含む）を確認し、README.md以外の製品変更を拒否する。工程文書5領域は本依頼の成果物だけをリストで識別し、無関係な変更を除外しない。

## Risks / Trade-offs

- [候補のv1.10省略が未承認] → 文案と省略の判断を個別に確認し、最終文・検証基準・承認者・文書版を一組にしてPM仕様承認まで実装を止める。差替え文に旧候補の承認を流用しない。
- [原本が古くなる] → 実装開始前に対象外変更を照合し、発見時は自動復元せず比較原本の更新をPMへ確認する。
- [5語を含むだけで明確化と誤認] → 1行だけから用途を平易に言い換える品質判断を併用する。実測していない理解度向上を主張しない。

## Migration Plan

データ移行・配備変更なし。承認→計画→検証のRED→3行目のみ編集→GREEN→独立品質の順。問題があれば当該行の変更だけを取り消し、他行・他ファイルを復元し直さない。カード単位のcommit/pushは依頼branchだけに行う。

未承認の文案・省略・検証基準は安全に後回しにできる設計上のunknownではなく実装開始前の承認gateであり、open-questions.mdへ集約する。
