# Design

## Context

動機と対象は proposal.md、振る舞いは specs/wordfreq-cli/spec.md を参照する。既存のHTML整形部品は絞込み・top後の `pairs` と適用前の `total` を受け取り、表より前にメタ情報を出す。新しい部品境界を作る必要はない。過去のHTMLバイト期待値・CSS/class厳密検査との整合方法と、「横」の描画確認を実装前に明確にするため、この局所設計記録を作る。別のBMAD Architecture文書は不要。

## Goals / Non-Goals

**Goals:** 最終表示対象を唯一の件数根拠とし、既存の総出現回数表示の横に読めるテキストとして追加する。既存の安全な静的HTMLを維持する。

**Non-Goals:** CLI引数や共有選択処理の変更、再集計、JSONメタ情報、レイアウト全体の再設計、新しい検証サービスは行わない。

## Decisions

- 件数は既存 `format_html(pairs, basename, total)` 内で `len(pairs)` を使う。呼出し元の追加引数や入力再走査より小さく、実際の表データ行数とずれない。総出現回数は既存の `total` のままとする。
- 総出現回数の値と同じ表示区画の横に `表示 N 種類` を置く。別の縦積みメタ項目や表の列追加は要求の「横」に合わない。DOM class/CSSの具体形は最小限の実装裁量とする。
- テストは既存の整形部品・CLIのファイルへ追加する。既存HTML期待値は正当な出力差分だけ整合させる。封印済み過去baseline原本は変更せず、今回用の固定期待値またはテスト内の明示的変換を使う。text/jsonの保存済み期待値は変えない。
- HTMLの文字列・DOM順だけでは位置確認に不十分。品質は対象headのCLI生成HTMLを通常幅1280×900と狭幅320×900で独立して描画確認し、総数横の配置・読みやすさ・非重複を確認する。既存の静的安全性と表の可読性も維持する。

## Risks / Trade-offs

- [固定3、top値、絞込み前件数の取り違え] → 1・3・10・12・0のケースと、上限・下限・topを併用するケースを検証する。
- [旧HTML検査が新表示を拒否する] → HTMLの意図した差分を明示して期待値を整合する。過去依頼の製品snapshot固定によるscope gateは今回の合否と区別し、無断で緩めない。
- [メタ情報追加で狭幅の内容が重なる] → 実描画で新文言と総数・表が欠けず読めることを確認する。必要最小のレイアウト差分以外は変更しない。

## Migration Plan

データ移行・依存更新はない。通常のリリースでHTML生成結果にのみ表示が加わる。問題時は今回の表示・対応テスト・README追加の変更を戻す。保存済みHTMLを書き換える仕組みは作らない。未決事項はない。
