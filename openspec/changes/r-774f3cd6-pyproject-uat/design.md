# Design

## Context

動機と変更範囲はproposal.md、契約はspecs/package-metadata/spec.mdに従う。現物にはdescriptionが無いため、OQ-1は実装前に仕様承認PMで解消する必須条件であり、延期可能な技術課題ではない。BMAD partialの回答集約規則に従い文書化まで進めるが、実装可能とは判定しない。Architectureの変更は不要。

## Goals / Non-Goals

**Goals:** 承認されたbeforeを固定し、指定文字列の追加と無関係な差分の排除を直接確認できるようにする。

**Non-Goals:** 新設権限・空文字・説明文を推測しない。依存、製品試験ファイル、CIを追加変更しない。

## Decisions

- OQ-1回答前は製品編集を行わない。欠落を空文字扱いする案は、既存値への追加という依頼を改変するため採用しない。新設が承認される場合は元値と受入条件も仕様改訂へ反映してから計画する。
- 承認後は対象descriptionの必要箇所のみを編集する。TOML全体の再シリアライズは無関係な整形を招くため使わない。
- 検証はPython標準tomllibによる前後解析とdescription除外後の構造比較、git差分の目視確認を組み合わせる。実行可能な検証スクリプトが必要なら工程管理領域に置き、製品ファイルの追加変更を避ける。具体的な実行コマンドは計画で確定する。
- 品質の証拠はhead・基準commit・コマンド・終了コード・条件ごとの結果を文字の検証文書に残す。PMに画像や圧縮ファイルの展開を求めない。

## Risks / Trade-offs

- [既存値が無い] → OQ-1解消を実装開始条件とし、現状で値の完全一致を合格にしない。
- [型付き比較だけでは書式変更を見逃す] → git差分も確認し、description以外の編集が無いことを照合する。
- [工程成果物を製品差分と混同する] → `.planning/`、`openspec/`、`_bmad-output/` の工程成果物を分けて一覧化する。
- [差分の基準が途中で変わる] → 承認したbeforeのcommitと値を検証記録へ固定する。現時点の実装前commitはb34cba0d008923e7f5267ce52d5403492ea53925でありdescriptionは欠落。
