# Tasks

OQ-1未解消のため本一覧は実装着手の承認ではない。仕様承認PMが回答を集約し、必要なBrief・PRD・OpenSpecの改訂を終えるまで、以下の製品作業へ進まない。

## 1. descriptionの一点変更と直接検証

- [ ] 1.1 OQ-1回答と仕様承認を照合し、対象repo・branch/commit・ファイルパス、実装前基準commit・連結元文字列・変更権限を工程検証記録に固定する。検証：記録と承認原文の一致、承認対象の現物との一致、欠落元値を推測していないことを確認する。未解消なら製品編集せずPMへ返す。
- [ ] 1.2 工程管理領域に受入検証を用意し、計画で具体的なコマンド・基準取得方法・期待結果を確定する。検証：未編集TOML解析と承認基準の取得は成功し、suffix未追加による値の完全一致検査が期待どおり失敗することを記録する。新設案の場合は承認改訂済み受入条件に合わせる。製品試験ファイルやCIは追加変更しない。
- [ ] 1.3 編集直前に現物と承認基準を再照合し、不一致なら停止する。一致していればdescriptionだけに正確なASCII ` (UAT)` を1回連結する。検証：編集後TOML解析成功、変更後descriptionと承認済みbefore.descriptionにASCII ` (UAT)` を1回連結した値との完全一致、description除外後の全項目一致、git差分と未追跡ファイル一覧で他項目・書式・依存・他製品ファイル不変を確認する。製品変更を含むcommit、対象ファイルのSHA-256、コマンド・終了コード・条件別結果を文字の証拠として記録する。

## Workflow follow-up

- 品質は同じ製品commitと対象ファイルのSHA-256を照合し、条件を独立に確認して文字の検証記録を添付する。PMに画像や圧縮ファイルを開かせない。
- 受入と最終確認の後にOpenSpecをsync・archiveする。受付light指定からfullへ切り替えた理由（危険なパスpyproject.toml）を最終報告へ引き継ぐ。
