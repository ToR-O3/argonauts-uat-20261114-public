# Design

## Context

動機と対象はproposal.mdを参照。製品の設計変更はない。同じ例の検証であること、README限定と工程証拠の区別を、実装前に明確にするための作業設計だけを記す。BMAD Architectureは不要。

## Goals / Non-Goals

**Goals:** 1つのREADME例と3形式の実行を直接対応させ、PMが文字原本から判定できるようにする。

**Non-Goals:** 新機能、新しい試験・検証ツール、既存HTML全般の再設計、過去依頼の全条件の再実装。

## Decisions

- READMEの既存起動表記に合わせ `python -m wordfreq input.txt --min-count 3` を1つ追加する。3つの例の掲載は選ばない。既存説明と末尾行は維持する。
- UTF-8の同一入力内容を3形式に使う。textは例そのもの、json/htmlは形式指定だけを追加し、top等を変えない。検証入力には3回以上と3回未満の語を含め、空結果だけによる誤合格を防ぐ。
- textの回数とタブ区切り、JSONの配列とword/count、HTMLの順位・単語・回数の表、basenameとフィルタ前総数を既存契約に照合する。表示行の和をHTML総数と誤認しない。
- 検証原本は `_bmad-output/initiative-r-5f8197e8/` 配下の文字文書へ保存し、実行したコマンド・作業場所・入力パスと内容・各exit・stdout/stderr・期待値と確認結果・検証headを追跡可能にする。分離した出力原本にはパスを付す。PMに画像や圧縮ファイルを開かせない。品質が画像を確認した場合も枚数・内容・結果を文字文書に記録する。
- 入力と生成出力は検証用一時データまたは工程証拠として扱い、製品fixtureや試験ファイルにはしない。コード修正が必要になったら範囲を広げずPMへ返す。

## Risks / Trade-offs

- [例と違う条件で実行してしまう] → 完全なコマンドと同一入力内容を3形式分記録する。
- [終了コード0だけで誤合格] → 語と回数、閾値未満の除外、形式固有の構造を照合する。
- [依頼範囲の拡大] → 全git差分を工程成果物とREADMEに分類し、コード・設定・依存・試験に変更がないことを確かめる。

移行は不要。READMEの局所追加を戻せば文書変更を取り消せる。未決事項はなし。ここに実行結果は含めない。
