# Design

## Context
動機と変更範囲はproposal.md、動作契約はspecs/wordfreq-cli/spec.mdを参照。現行はFileSource→iter_tokens→Counter集計→top_words→text/json整形。top_wordsは回数の後に語の昇順で並べ、CLIはtop後のpairsだけを整形する。HTMLではtop前の総数とbasenameも必要になる。モジュール横断の値渡し・HTML注入対策・互換性変更のため、この局所設計を記録する。

## Goals / Non-Goals
**Goals:** 既存の部品境界を保ち、集計順序・全体総数・HTML表示の責務を分離する。実CLIでHTMLを再生成し、実装担当とは独立して検査可能にする。
**Non-Goals:** 入力境界やトークナイザの再設計、汎用テンプレートエンジン、クライアントスクリプト、依存追加。製品範囲外はproposalを参照。

## Decisions
1. **集計時の初出情報を保持する。** 正規化トークン列から作ったCounterの挿入順を利用し、回数だけをキーにした安定ソートで同数の初出順を保つ。語の昇順や集合経由の再構築は行わない。明示的な位置mapを別に持つ案より現在の順序保持機構を使う方が局所的。top_wordsの部品契約にも「countsの挿入順が初出順」を説明し、CLIからの経路と単体の両方で試験する。
2. **総数はtop前のCounterから計算する。** CLIはcounts、sum(counts.values())、top後pairsを別の値として扱う。表示pairsからの総和は誤り。basenameの取得は実行環境のパス規則に従う。HTMLへは元パスではなくbasenameだけを渡し、タイトルや属性に元パスを漏らさない。text/jsonの引数と出力構造は変えない。
3. **HTML整形は純粋な部品にする。** pairs・basename・totalを受け取り、文書文字列を返す。既存formattersへ追加し、CLIがhtmlだけへメタ情報を渡す。入力文字列は標準のHTMLエスケープを使い、文字データの位置だけに入れる。文字列置換の独自エスケープやJSテンプレートは採用しない。特殊文字のある語は部品直接試験、basenameは実CLIでも検査する。CSSとタグは固定し、データをCSS・属性・URL・スクリプトへ挿入しない。
4. **静的な明るいレスポンシブ表。** UTF-8宣言とviewportを持ち、見出し・入力情報・表の順。意味のあるtableヘッダ、内包CSS、システムフォントを使う。単語列とbasenameを折り返し、固定の最小幅・省略・overflow隠しで収めたふりをしない。順位と回数は狭い幅に収まるよう設計する。外部フォントやCSS、画像、JSは不要。細かなUI寸法は承認後の公式UI設計で検証する。
5. **幾何と画像を組み合わせる。** ブラウザ用の検査補助は製品HTMLのスクリプトではなく、後続のローカル検証手段として用意できる。Range.getClientRects等で文字の行断片をそのまま保存し、viewport・要素・切取り祖先・隣接内容の矩形と照合する。要素自身への縦包含だけを必須にせず、横方向の収まり、切取り祖先内の収まり、隣接内容との非重複、実画像での可読性で判定する。DOM文言やscrollWidthだけでは合格にしない。
6. **独立再現と証拠。** Builderの自動試験と品質の実CLI再生成を区別する。品質は対象headと入力原本からHTMLを作り直し、通常幅・320 CSS pxの画像を実際に読んで幾何原本と合わせて判断する。HTMLの外部リソース参照の静的検査、外部通信の試行記録を併用し、通信を遮断しただけの成功を無通信の根拠にしない。証拠不足や環境不足は未検証として返す。

## Risks / Trade-offs
検証条件は、後続のUI設計・PLANで通常幅のCSS px値と対象ブラウザを固定し、実行時の版を保存する。長い連続語とbasenameの入力を固定し、320 CSS pxで実際に折返しが起きることを確認する。複数桁の順位・回数・総数も表示検査へ含める。品質は対象コミットの製品コードを実行していることを、開始時の作業状態と差分で確認し、未コミットの製品変更があれば対象headの証拠として採用しない。
通信観測は対象文書を開く前から表示確認終了までとし、文書に起因する要求・遷移と失敗した通信試行も記録する。ブラウザ背景通信は文書との因果関係を確認して区別し、根拠なく除外しない。名前の連続空白・改行・タブは空白保持と折返しを両立するCSSで表示し、HTMLエスケープだけに頼らない。UTF-8宣言と実際の保存バイト列の一致を検査する。非Unicodeのファイル名の新しい入力契約や双方向制御文字の表示変換方針は、本変更の確定仕様へ追加しない。
- [旧利用者が語の昇順を期待] → 同数時の意図した変更を利用説明・仕様・試験へ記録し、text/json/htmlの共通試験を置く。
- [top後の値から総数計算] → 頻度の違う複数入力とtopの組合せで総数を固定して検査。
- [basenameと語の注入] → テキストとしてエスケープし、DOMの表示値・余分なタグ・イベント・通信の有無で確認。
- [長い語/名前の横はみ出し、文字Rangeの縦差] → 生の矩形と画像を保存し、指定された合否基準で判定する。測定値の改変や縦条件の勝手な追加をしない。
- [ブラウザ検証の未実施を自動試験で代用] → head・コマンド・入力・画像・矩形・通信記録を条件へ紐付け、品質が独立確認する。

## Migration Plan
仕様承認後に計画・実装・独立品質確認を行う。語順の期待値は初出順に更新し、HTML使用例を追記する。CIは変更しない。問題があれば通常の差戻しで直し、マージ済みの変更の取り消しは人/PMの判断に従う。永続データ移行や移行用フラグは不要。新しいAPI・入力方式を追加して回避しない。
