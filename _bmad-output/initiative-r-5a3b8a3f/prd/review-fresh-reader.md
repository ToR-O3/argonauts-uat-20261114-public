# Fresh-reader review — prd-wordfreq-cli.md

Reviewer: fresh reader (this document only). Date: 2026-11-17.

## Verdict

この PRD は決定的挙動（トークナイズ、正規化、ソート、エラー出口、テスト範囲）が FR ID と D 決定に紐づいており、下位の spec writer がそのまま OpenSpec 変更におろせる水準で、方向性のやり直しは不要。ビルド・受け入れを止めうる穴は 3 点だけ（入力エンコーディング未規定、ファイル引数の個数の挙動、CI/終了コードの受け入れ可能性）で、いずれも design.md か specs で 1 行決めるか FR-1 に追記すれば閉じる。

## The three fixes that matter most

1. **FR-1 の「デコードできない」が、どのエンコーディングかを書いていない。** UTF-8 固定なのかロケール従順（`open()` の default）なのかで、同じファイルに対する正常/エラー判定が変わり、「同じ入力で決定的」（FR-4）の前提そのものが揺らぐ。Windows と Linux CI で結果が割れる唯一の地点なので、「入力は UTF-8 と仮定し、それ以外で失敗したら FR-1 のエラー出口」を明記する。
2. **ファイル引数が 0 個のときと複数個のときの挙動が未定義。** `python -m wordfreq`（無引数）が使い方エラーなのか stdin を読むのか（stdin は Non-goals 寄りだが未明記）、`file1 file2` が使い方エラーなのか連結なのか。受け入れ側が UJ-3 とは別に境界ケースを判定できない。argparse の既定（無引数=使い方エラー）でよければ FR-2 の使い方エラー列挙に「ファイル引数 0 個・複数個」を追記する。
3. **「CI で通る」（FR-7）が検証可能か、終了コードの値まで固定するのか、をどちらか決める。** CI がリポジトリに既にあるなら「CI」とは何かは不要だが、無いなら CI 追加が作業範囲になる（pyproject のみ許可の FR-8 と衝突し得る）。終了コードは「非 0」で受け入れ可ならそれで通旨を、値（使い方=2、I/O・デコード=1 等）を識別子にするなら FR に値を書く。受け入れテストの断言レベルがここに決まる。
