# 限定PRの整備は工程原本の保全を先行し、新headの全差分を独立確認する

## Context

READMEの1行追加でも、full工程の成果物が積まれたPRは「変わったファイルがREADMEだけ」という条件を満たさない。工程pathを除いた一覧で合格にするのも、原本を失う形で工程文書を除去するのも解決ではない。

依頼 `r-d78495de` の整備カード `t_8a8f9019` の標準添付118（D5-HANDOFF.md、以下はKanban原本名でありrepo内pathではない）は、全履歴の工程archiveが37MBとなり、25MBの添付上限で拒否されたことを記録した。解決は圧縮率の追求ではなく、**既存履歴の保管と、今回変更原本の配送を分けること**だった。今回の工程原本を欠損なく列挙し、小さな標準添付へ保存してからPRを整備した。

この学習が残すのは、製品ツリーだけでは復元しにくい保存対象の選び方と確認順序である。Git原本、添付、受取側の読取りを区別する一般原則は既存学習を参照する。

## Guidance

1. **保存対象の列挙と、受入対象の全差分を分ける。** 保存では固定したbase・保存commit間の工程変更を列挙してよい。一方「READMEだけ」の受入ではpathを除外せず、実PRのbase/head・merge-baseを固定した全変更一覧を読む。保存対象を絞った一覧を、そのまま受入の全一覧として転用しない。
2. **PR整備より先に保全を成立させる。** 保存commitのpush済み・祖先保持を確認し、今回変更原本の一覧、原本を収めた標準添付、その保存実体とGit原本の一致を確認する。必要なPLANと品質の文字原本は、archiveだけでなく後続PMが読める形でも渡す。
3. **容量超過と内容ガードの拒否を混同しない。** この事例では今回変更原本を全件保持し、以前の原本は既存Git履歴と既存添付に保持した。秘密判定の拒否を圧縮・改名で回避する許可ではない。対象の欠落、削除原本の取りこぼし、未追跡原本の未保存があれば、必要な保全が成立するまで整備に進まない。
4. **限定化は承認された手順だけで行う。** この事例ではbaseのツリーへ一括で合わせ、承認済みREADMEのblobを戻す追加commitを作った。保存commitを祖先に残し、fast-forward pushした。個別の工程文書削除、強制push、branch削除、履歴書換えを代替にしない。これは各依頼の固定入力・PM判断に従う操作例であり、任意のbranchに無条件で適用する手順ではない。
5. **新headを別の確認対象にする。** Builderの整備後自己確認は独立品質の代わりにならない。品質が実PRの対象を読み直し、除外なし全一覧とREADME両原本・全patchから各条件を再判定する。PMはその新しい文字原本を読み、旧headの未達を上書きせず、解消後の判断を別に記録する。

## Why This Matters

PRの差分が小さいことと、工程原本が保全されたことは独立の条件である。差分だけを見れば証拠喪失を見逃し、保存commitだけを見れば受取側が読めない状態や、PRへの工程文書再混入を見逃す。

この境界は製品のpytestでは検出できない。既存CIはpytestを実行する（`.github/workflows/pytest.yml` の `pytest` job）。カード添付の配送や、PMによる文字原本の読取りまで保証する試験ではないため、製品コード・依存・新しい検証サービスは追加せず、証拠の帰属と操作順序を残す。

## When to Apply

- 指定ファイルだけのPRと、full工程原本の保存を両立するとき。
- 全履歴archiveが大きすぎるが、今回必要な原本を欠損なく特定できるとき。
- PR整備後の最終化で工程資料を作業用に復元するとき。作業用復元を、そのまま追跡ツリーへ戻さない。

## Examples

以下の数値と状態はこの依頼の記録であり、一般的な上限や他の依頼の合格を主張しない。

|段階|原本に記録された事実|証拠|
|---|---|---|
|整備前の品質観測|全61件、README以外あり、条件2未達・暫定、human_needed|フェーズ検証 `t_5c607fb0` run86、添付108/109|
|保存起点|品質文書追加後は全67件（READMEと工程原本66件）。工程原本を全件保存|整備 `t_8a8f9019` 添付118の「保存と照合」|
|標準添付|今回工程原本66件のarchiveは111439 bytes。添付実体と原本をSHA-256/cmp/tar比較|同カード添付117、118。品質添付121ではGitから取り出した66件との全一致も確認|
|整備後の独立確認|PR全差分READMEだけ、+1/-0。指定例1行と既存保持を条件別に合格|同カードrun92、添付121/122|
|最終化|作業用原本でOpenSpec 2.1更新・archiveを行い、PRのREADME限定を維持|最終化 `t_0c1d95a6` 添付124（FINALIZATION.md）|
|最終品質|同じ最終headの全一覧・READMEを再確認し合格|同カードrun95、添付125|

実PRは `ToR-O3/argonauts-uat-20261114-public#19`。2026-11-25の学習準備時、取得した基準branch `v112-a` にそのマージcommitと保存commitが到達可能であり、整備後のbase...headはREADMEだけだった。過去の未達記録やphase未完了を、最終品質合格によって遡って完了扱いにはしない。

依頼者の2026-11-25T06:53+09:00の判断で3形式の製品実行は対象外となった。この例を「README変更なら常に実行不要」という免除に広げない。本学習準備も製品実行を再実施したものではない。
