# 証拠の配送は添付成功ではなく受取PMの原本読取りまで確認する

## Context

wordfreq HTMLの受入カード `t_bf63de81` は、品質が検証を終えた後でも証拠配送で二度止まった。品質の正常完了run121（`t_c9dd351a`）は検証対象head `7c704f3` の独立検証を報告したが、大型のraw・derived・画像原本は品質profile内に保存されていた。品質の添付原本 `cli-evidence.md:21` は、repo外保管とcommitした一部JSONを明確に区別している。保存先の存在は、PMがその原本を読めることを意味しなかった。

以下は受入カードのコメントと正常完了run127の実録であり、一般の全PMの能力を述べるものではない。

1. run124はAC4/AC6の必須原本が標準添付に足りず、`needs_input`で停止した。
2. 人が標準添付128のアーカイブ、138のSHA一覧、主要JSON等を提供した。しかしrun125のPMにはterminalがなく、`read_file`はgzを読めなかった。今度は添付不足でなく展開能力の不足として`capability`で止まった。
3. 人が既存添付をPM workspaceへ元の相対pathのまま安全展開した。絶対path・親への脱出・symlinkを拒否し、通常ファイル190件のSHAが添付138と一致したという人の回答をPMが採用した。
4. PMは展開済み原本を`read_file`/`search_files`でAC別に照合してapprovedにした。PNG再閲覧、試験再実行、SHA再計算を自分で行ったとは主張していない。

旧コメントの「183＋11件」は人が190件へ訂正している。件数は訂正後の実録に従い、初期コメントを再利用しない。

## Guidance

証拠受渡しでは次の三段階を別々に記録する。

|段階|確認すること|まだ言えないこと|
|---|---|---|
|保存済み|原本の保管先、対象head、run/root、保持期間を特定できる|別profileから読める、標準添付された|
|標準添付済み|添付IDと実際の保存ファイルを一覧で読み戻せる|受取側に展開手段がある、中身を照合済み|
|受取側で読取り済み|必要な原本をその担当の利用可能ツールで開き、要求と照合できる|その担当自身が製品試験や画像実閲覧を再実施した|

- **配送先の能力を先に確認する。** JSON索引だけでなく、索引が指すraw・derived・CLI入出力・通信原本まで読める形式を用意する。archiveだけ渡すなら、受取側が展開できるか確認する。機能がなければ、許可された経路で読める個別添付、または人による受取workspaceへの安全展開を求める。
- **原本の相対pathを保つ。** 同名のrawや画像が多数あるため、名前の平坦化で対応を失わない。対象head/run/rootと全ファイルのSHA一覧を一緒に渡す。品質profileの絶対pathだけを配送完了の根拠にしない。
- **安全展開と照合の実施者を書く。** 展開前に絶対path、親への脱出、symlinkなどを拒否し、通常ファイルだけを受取先の専用領域へ展開してSHA一覧と照合する。人の回答を根拠にしたら「人が確認」と書く。SHA一致はバイト同一性であり、PNGの可読性や試験合格そのものではない。
- **既存のガード拒否を迂回しない。** 圧縮・リネーム・別profileの直接参照で拒否された内容を通さない。今回のarchiveは人が標準添付した原本の配送例であり、Botによる秘密ガード回避の許可ではない。製品や証拠を再生成せず既存原本の配送だけで解消できる場合は、その範囲に留める。
- **不足と解消を別記録にする。** 添付後は「未添付」を繰り返さず、残る障害が展開能力なのか、原本照合なのかを特定する。解消後は添付ID、展開先、照合方法、実施者、未実施事項を記録する。

## Why This Matters

コードの試験では、別担当にどのツールが渡されるかを保証できない。原本保全のrunbook（`docs/wordfreq-html-verification.md:123-125`）があっても、受入の配送先がarchiveを読めるとは限らない。この境界を記録しないと、品質完了後に再探索・再添付・再blockが発生し、さらに「保存済み」を「添付済み／確認済み」と誤報する。

この教訓は配送の運用条件であり、新しい集計サービスや製品コードで自動化しない。原本の内容や判定を手で直すことでもない。

## When to Apply

受入PM、レビュー担当、報告担当へ、別profileに保管した大型証拠を渡すとき。受取側が読む必要のある証拠だけを、その担当の許可された能力で配送する。全員にterminalを追加することを前提にしない。

## Examples

```text
NG: quality profileに全raw/PNGを保存した → PMへ絶対pathと要約だけ渡す → 原本照合済みと報告
NG: archiveを添付した → PMには展開ツールがないが配送完了と扱う
OK: 添付IDを読み戻す → PMの読取り能力を確認 → 必要なら人が安全展開しSHA照合
    → PMが原本をACと照合 → 人のSHA確認・品質の画像実閲覧・PMの文書照合を別記録にする
```

実例の証拠帰属は、検証対象head `7c704f3`、報告commit `8a2372f`、最終化品質head `39b7b85`を分ける。マージ待ち `t_87ce49fc` は、通知head `1319222` が品質確認headと違うため `unverified_merge=true` と記録した。これらの旧headの成功を通知headへ流用しない。本学習もマージ対象headの試験を再実施したものではない。

## PMの画像閲覧方法を代替するときの限定記録

配送先で原本を開けることと、その担当が必要な判定を行えることも別である。`--min-count` のフェーズ判断 `t_a60abb2e` では、原本を展開してもPMにPNG閲覧手段がなく、runbookが求める画像確認をそのまま実施できなかった。添付やSHA一致をもって閲覧済みとはせず、人へ不足を示した。

同カードの人の明示承認を、標準添付199 `PM-READ-DECISION.md:10-15,17-24,47-50` は次のように限定して記録した。受入 `t_9f464654` の標準添付220 `ACCEPTANCE-DECISION.md:27-35` も同じ境界を引き継いだ（これらはKanban添付の文書名であり、repo内のファイルではない）。

- **承認と範囲**：人の13:03回答は、PM本人のPNG実閲覧を「品質本人の `final-01` の142画像実閲覧記録＋PM本人のHTML・raw・CLI原本確認」で代替することだけを認めた。品質の独立実閲覧や、画像以外の原本確認を省略する許可ではない。
- **同一性の実施者**：人の12:52回答による618件のSHA一致を採用した。PMによる独立計算ではなく、全618ファイルの全行読了でもない。
- **証拠の帰属**：製品検証headは `afaa56f`（694件成功、`final-01`）、品質報告headは `421a65c`。この組を後のheadに付け替えない。
- **未実施**：PMはPNG未閲覧、試験未再実行、SHA未再計算と明記し、AC別の原本path・SHA・実際に読んだ範囲を判断記録に残した。

この事例は「画像を見られなければ常に他者の台帳でよい」という恒久的な免除ではない。同じ方法を別の依頼へ使う場合も、まず要求された確認方法と担当の能力を照合し、代替が必要なら人の明示承認と対象・範囲を記録する。承認なしで未達gateを合格へ進めない。配送手順があることだけでは、人の判断が必要な代替条件を回帰試験で保証できないため、この運用上の境界を残す。

また、このPM判断はマージ前受入であり最終品質印ではない。最終化 `t_68f21475` の正常完了run167は、別の最終品質head `abb7a63` に対して `final-04`・702件成功・142画像実閲覧を報告している。古い `final-01` の結果を新headの合格へ昇格したものではない。head更新時の全面再検証は `docs/wordfreq-min-count-verification.md:120-124` の規則に従い、本節の画像確認方法の代替をCI・新head・マージの許可へ広げない。
