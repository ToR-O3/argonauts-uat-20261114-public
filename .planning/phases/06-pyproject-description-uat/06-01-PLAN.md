### CLI, functions, exit and condition schema

新関数 `verify_content(baseline: bytes, candidate: bytes) -> dict`、`collect_repository(root, baseline_commit, product_commit, process_paths) -> dict`、`main(argv=None) -> int`。モジュールimportで実行/書込みしない。CLI prefixは `python3 -B .planning/argonauts/r-774f3cd6/verify_description.py`。

- `preflight --baseline COMMIT --candidate PATH --inputs JSON --process-paths JSON`：固定repo/branch/承認入力、基準・現物欠落、全bytes一致、全Git状態の既知工程差分のみを判定。製品commit不要。
- `content --baseline COMMIT --candidate PATH`：固定基準blobと候補ファイルの内容判定。COMMITはこのPLANの基準full ID以外拒否（隔離自己テストは関数へbytesを直接渡す）。
- `expect-red --baseline COMMIT --candidate PATH --inputs JSON --process-paths JSON`：preflight成功後contentの実測結果を得る。inner_exit=1かつfailures=[VALUE_EXACT]でその他すべてPASSの場合だけouter exit0。inner結果を消さず出力。一般の非0を期待REDとしない。
- `repository --baseline COMMIT --target-record JSON --process-paths JSON --actor builder|quality`：06-02が作るproduct-target.jsonのfull製品commitを読み、固定blobと実入力・全Git状態を判定する。可変HEADを製品比較先にしない。

全モードstdoutはUTF-8 JSON単一object（文字でそのまま証拠へ収録）：schema_version=1、mode、argv、cwd、actor、baseline_commit、product_commit（未確定時null）、head_start/head_end、hashes（baseline_blob_sha256/candidate_blob_sha256/actual_input_sha256/verifier_sha256/selftest_sha256/process_paths_sha256）、conditions配列、failures配列、exit_code、error（通常null）、git_state（scopeごとの全path/status/mode/blobとpatch全文）。conditions各要素はid、status=PASS|FAIL|SKIP、detail。未評価条件は理由付きSKIP、最終合格で必須SKIP不可。stdoutのexit_codeとOS終了値は一致。expect-redのみinner_result/inner_exit/outer_exitを別欄とする。stderrも空であっても記録する。

exit0=評価対象全条件合格、exit1=要件不一致、exit2=入力取得/環境/内部エラー。候補不正TOMLはCANDIDATE_PARSE FAIL/exit1、基準不正/取得不能、読取不能、Git失敗、内部例外はexit2（error.typeとdetail）。argparse不正もexit2。欠落キーは存在確認で処理しKeyErrorを期待失敗にしない。

内容必須条件：BASELINE_FETCH、BASELINE_PARSE、BASELINE_DESCRIPTION_ABSENT、CANDIDATE_READ、CANDIDATE_PARSE、VALUE_EXACT、STRUCTURE_UNCHANGED、BYTES_UNCHANGED。VALUE_EXACTはproject所属のstring固定値と許可description行1件を一体で判定。欠落時にはこの条件だけFAIL、構造除去は存在時のみ、行0件時のバイト比較は候補そのものを使う。存在時はproject内version行直後の許可行だけを行境界/位置/件数を限定して除去する（全体replace/strip/改行正規化禁止）。追加行の改行種別は基準version行と同じとし、その1行を除いたraw bytesが基準全体と完全一致。全体tomllib解析後、deep copyからproject.descriptionだけを除去し全構造を比較する。最終GREENはVALUE_EXACTもPASSが必須。

preflight追加条件：APPROVAL_BINDING、REPO_IDENTITY、REQUEST_BRANCH、CURRENT_DESCRIPTION_ABSENT、CURRENT_BYTES_BASELINE、PROCESS_PATHS_VALID、TREE_SCOPE、INDEX_SCOPE、WORKTREE_SCOPE、UNTRACKED_SCOPE、IGNORED_INVENTORY。repository追加条件：PRODUCT_COMMIT_FIXED、PATCH_ONE_LINE、MODE_UNCHANGED、BLOB_INPUT_SHA256、TOOL_HASHES、HEAD_STABLE、および上記scope条件（欠落専用条件はrepositoryには適用しない）。各条件の誤動作はそのidのFAILまたはexit2で観測する。

Git取得はshell=Falseのargv、当該runで選択・照合済みの現在カードrootを固定cwdとして用い、binary `git show COMMIT:pyproject.toml` で取得する。計画カードの絶対worktreeを埋め込まない。baseline/製品blob本文のSHA-256はhashlibで計算（Git object IDと別）。repositoryは自身で取得したblob bytesをverify_contentへ渡し、同bytesのSHAをactual_input_sha256へ記録し、working fileもblobとbytes/hash一致を要求する。入力上限1MiB、越過はexit2、subprocess timeout30秒はexit2。fixtureは `$TMPDIR` 配下（active profile scratch）にTemporaryDirectoryで隔離、実製品へ負例を書かず残存させない。

全Git状態：固定基準→製品commit（preflightでは現在full HEAD）を `git diff --raw --no-abbrev --no-renames -z BASE PRODUCT --`、cached→PRODUCT、worktree→indexを別々に同形式で取得。さらにPRODUCT→worktreeの生patchを `--no-ext-diff --no-textconv` で取得し、staged/unstaged相殺を見逃さない。`git status --porcelain=v1 -z --untracked-files=all --ignore-submodules=none` と `git ls-files --others --ignored --exclude-standard -z` を取得。改名はno-renamesの削除+追加両pathとして全件分類、mode/型/追加削除/submodule/unmergedも確認。全scopeを人が読める文字へ展開する。製品はpyprojectの許可1行、他は用途審査済みexact pathsだけ。ignoredも全件表示し、既存cacheを許容するなら各exact pathと用途/根拠を記す。未知工程コード、未知未追跡、未知ignoredを黙って除外しない。
