# Proposal

## Why

テキストファイルから単語の出現回数を知りたいとき、専用の形がなく即席のパイプライン（推定。依頼に現状運用の記述なし）を組みがちである。依頼 r-5a3b8a3f は、`python -m wordfreq` で1コマンドで語頻度を確認できる小さな CLI ツールの追加を求めている。挙動（正規化・並び順・エラー出口）を決定的にし、テストで固定することが価値の中心。

## What Changes

- 新しい Python パッケージ `wordfreq` を追加し、`python -m wordfreq <file>` で実行できるようにする。
- `--top N`（既定 10）で表示件数、`--format text|json`（既定 text）で出力形式を指定できる。
- 「切り出し・正規化」「集計」「入力取得」「出力整形」を部品として分離し、入力元（標準入力・URL）を後から追加できる構成にする。構成判断を design.md に記録する。
- pytest による単体試験を追加し、CI の pytest ジョブで通るようにする。
- ランタイム依存は標準ライブラリのみ。パッケージ化に最低限の設定ファイル（`pyproject.toml` 等）は許容（危険なパスのため人の承認対象になり得る）。

画面（UI）は作らない。日本語形態素解析は v1 範囲外（トークナイザの差し替え点だけ残す）。

## Capabilities

### New Capabilities
- `wordfreq-cli`: テキスト読み込みから語頻度の集計・出力までの CLI 挙動（実行方法、件数・形式のオプション、切り出し・正規化の定義、決定論的ソート、エラー終了、部品分離と入力元拡張の構成）。

### Modified Capabilities
（なし）

## Impact

- 新ディレクトリ `wordfreq/`（パッケージ本体）と `tests/`（pytest 試験）。
- `pyproject.toml` 等のパッケージ設定ファイルを追加・変更する可能性がある（smart マージ方針の危険なパス）。
- CI に pytest 実行ジョブが必要になる可能性がある（既存 CI の構成に依存。workflow ファイル変更は Bot の権限外のため、必要なら人の対応として扱う）。
- 既存コードへの影響なし（新機能の追加のみ）。

# Spec Delta

## Purpose

wordfreq CLI は、テキストファイルから単語の出現回数を決定論的に数え、上位 N 件を人が読むテキストまたは機械が読む JSON で出力する能力。切り出し・正規化、集計、入力取得、出力整形を分離した部品構成とし、入力元（標準入力・URL）の拡張判断を設計に記録できる状態を提供する。

## ADDED Requirements

### Requirement: 実行方法とファイル読み込み（FR-1）
`python -m wordfreq <file>` は、ファイル引数ちょうど 1 個を受け取り、そのファイルを UTF-8 として読んで頻度集計の結果を出力する。ファイルが存在しない・開けない・UTF-8 としてデコードできない場合は、エラーメッセージを stderr に出して exit 1 で終了する。ファイル引数が 0 個または 2 個以上の場合は使い方エラーとして stderr にメッセージを出して exit 2 で終了する。空ファイルは結果 0 件として exit 0 で正常終了する。

#### Scenario: 通常のファイルで語頻度が出力される
- **WHEN** 英単語を含む UTF-8 テキストファイルを指定して `python -m wordfreq <file>` を実行する
- **THEN** 正規化後単語の出現回数が多い順に上位 10 件が出力され、exit code は 0 である

#### Scenario: 存在しないファイルは非 0 終了
- **WHEN** 存在しないパスを指定して実行する
- **THEN** stderr にエラーメッセージが出て、exit code は 1 であり、stdout に結果が出力されない

#### Scenario: デコード失敗は非 0 終了
- **WHEN** UTF-8 としてデコードできないバイト列のファイルを指定して実行する
- **THEN** stderr にエラーメッセージが出て、exit code は 1 である

#### Scenario: 空ファイルは 0 件で正常終了
- **WHEN** 0 バイトのファイルを指定して実行する
- **THEN** 結果 0 件（text では出力なし、json では `[]`）で exit code は 0 である

#### Scenario: ファイル引数が 1 個でない
- **WHEN** ファイル引数なし、または 2 個以上で実行する
- **THEN** 使い方エラーとして stderr にメッセージが出て、exit code は 2 である

### Requirement: 表示件数オプション（FR-2）
`--top N` は表示する件数を指定する。既定値は 10。N は 1 以上の整数でなければならず、それ以外の値（整数でない、0 以下）は使い方エラー（exit 2）とする。結果の種類数が N より少ない場合は全件を出力する。

#### Scenario: 既定は 10 件
- **WHEN** `--top` を省略して、10 種類以上の単語を含むファイルを指定する
- **THEN** 上位 10 件だけが出力される

#### Scenario: 件数指定と全件出力
- **WHEN** `--top 3` を指定する
- **THEN** 上位 3 件が出力される
- **AND** 単語の種類数が 3 に満たないファイルでは全種類が出力される

#### Scenario: 不正な件数
- **WHEN** `--top 0` または `--top abc` を指定する
- **THEN** 使い方エラーとして stderr にメッセージが出て、exit code は 2 である

### Requirement: 出力形式オプション（FR-3）
`--format text|json` は出力形式を指定する。既定は text。text 形式は 1 語 1 行で単語と回数を読むことのできる形式とする（正確な列書式は design.md の決定に従う）。json 形式は `{"word": <str>, "count": <int>}` のオブジェクトを要素とする JSON 配列とし、要件「出力の順序決定論性」の並び順と一致する。不正な形式指定は使い方エラー（exit 2）。

#### Scenario: JSON 出力が機械可読
- **WHEN** `--format json` を指定して実行する
- **THEN** stdout が `json.loads` で解析できる配列であり、各要素が `word`（文字列）と `count`（整数）を持つ

#### Scenario: 不正な形式指定
- **WHEN** `--format xml` を指定する
- **THEN** 使い方エラーとして stderr にメッセージが出て、exit code は 2 である

### Requirement: 単語の切り出しと正規化（D-3）
単語の抽出は Unicode の単語構成文字（Python の `\w`、`re.UNICODE`）の連続する最大長とし、各トークンに `str.casefold()` を適用して正規化する。句読点・記号・空白は単語に含めない。大文字・小文字のみが異なる単語は同じ単語として集計する。トークナイザは差し替え可能な部品として実装する。

#### Scenario: 大文字小文字の同一視
- **WHEN** "Hello hello HELLO world" を含むファイルを text 形式で実行する
- **THEN** `hello` の回数は 3、`world` の回数は 1 として集計される

#### Scenario: 句読点を語に含めない
- **WHEN** "one, two. one" を含むファイルを指定する
- **THEN** `one` は句読点なしの語として 2 回に数えられ、`one,` のような語は現れない

#### Scenario: 空白区切りでない言語は未対応として振る舞いが決定的
- **WHEN** 日本語テキストを指定する
- **THEN** v1 は形態素解析せず、抽出ルール（`\w` 連続）による結果が決定論的に出力される（日本語対応は範囲外。差し替え点の存在は design.md に記録）

### Requirement: 出力の順序決定論性（FR-4・D-2）
出力は常に、出現回数の降順に並べる。回数が同じ単語は、正規化後単語の昇順に並べる。同じ入力ファイルと同じオプションでの実行出力は決定論的でなければならない。

#### Scenario: 同回数ワードは単語の昇順
- **WHEN** `apple` と `zoo` がともに 5 回出現するファイルを指定する
- **THEN** 両者は `apple`、`zoo` の順（単語の昇順）で出力される

### Requirement: 部品分離と入力元拡張の構成（FR-5・FR-6）
切り出し・正規化を行う部品と、集計・出力整形を行う部品を分離する。テキストを得る入力取得は解析・集計から境界として分離し、v1 のファイル入力もその境界の背後で動く。各部品は単体で呼んで検証でき、入力取得を介した集計経路を通過する試験を含むこと。入力元（標準入力・URL）の追加は入力取得境界の実装追加で足りるという構成判断を、変更の design.md に記録する。

#### Scenario: 部品が単体で検証可能
- **WHEN** トークナイザ部品と集計部品を単体で呼び出す単体試験を実行する
- **THEN** 各部品は CLI を経由せずに期待される入力・出力で検証できる

#### Scenario: 入力取得境界越しの検証
- **WHEN** 入力取得境界を介した集計経路の試験を実行する
- **THEN** 解析・集計は入力取得境界を介してのみテキストを受け取ることが確認できる

### Requirement: 試験と実行環境（FR-7・FR-8）
pytest による単体試験を用意し、リポジトリの CI の pytest 実行ジョブで通じる。試験は上記要件のシナリオ（不存在ファイル、空ファイル、引数個数、不正な `--top`・`--format`、同数語の順序、大文字小文字の同一視、UTF-8 デコード失敗、JSON 構造、部品単体・境界越し検証）を含む。対象 Python は当該 CI ジョブの CPython 3 の版とし、バージョン横断互換コードを書かない。ランタイム依存は標準ライブラリのみとする。

#### Scenario: CI で pytest が通る
- **WHEN** CI の pytest ジョブが実行される
- **THEN** 全試験が成功する

#### Scenario: 標準ライブラリのみ
- **WHEN** パッケージのランタイム依存を確かめる
- **THEN** 標準ライブラリ以外の依存が宣言されていない

# Tasks

実装順は部品（内側）から外側。各 task はその時点で pytest が通る状態を保つ。

## 1. 部品: トークナイザと集計

- [ ] 1.1 `wordfreq/tokenizer.py` を作成する（`\w` 連続抽出 + `casefold()`、差し替え可能な関数/注入点）。単体試験: 大文字小文字の同一視、句読点を語に含めない、underscore 語の固定、日本語テキストで決定的な出力（spec「単語の切り出しと正規化」）
- [ ] 1.2 `wordfreq/aggregator.py` を作成する（`count_words`、FR-4 ソートの `top_words`）。単体試験: 回数降順、同数は単語昇順、`--top` 超過時の全件、空入力

## 2. 部品: 入力取得と出力整形

- [ ] 2.1 `wordfreq/sources.py` を作成する（`TextSource` プロトコル + `FileSource`、UTF-8 デコード、`InputError`）。単体試験: 正常読み込み、不存在ファイル、デコード失敗、空ファイル
- [ ] 2.2 `wordfreq/formatters.py` を作成する（design D-A の `<count>\t<word>` 1行 と D-E の JSON 配列、0件は `[]`）。単体試験: text/json 双方の出力構造、順序の保持、`json.loads` 可読性
- [ ] 2.3 入力取得境界越しの試験を追加する（集計経路が `TextSource` を介してのみテキストを受け取ること、aggregator 系試験が FileSource 非経由であること。spec「部品分離と入力元拡張の構成」）

## 3. CLI 合成と実行形態

- [ ] 3.1 `wordfreq/__main__.py` を作成する（argparse: ファイル引数ちょうど1個、`--top` 既定10・1以上整数、`--format text|json` 既定 text。exit code 0/1/2 の分岐を design D-C どおりに）。CLI 試験: 正常系、`--top` 既定と指定、`--format json` 構造、不正値の exit 2、不存在ファイルの exit 1、引数個数エラー
- [ ] 3.2 `pyproject.toml` を追加する（`wordfreq` パッケージ、ランタイム依存ゼロ、pytest 開発依存）。`python -m wordfreq <file>` が repo 直下で動くことを確認
- [ ] 3.3 CI の pytest ジョブの有無を確認し、無ければ workflow 変更（人の対応）として block 判定の準備をする（proposal Impact 参照）
